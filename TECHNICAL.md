## 1. Goal and scope

The chatbot answers questions about Warhammer 40,000 from two sources:

- **The Core Rules PDF**, for rules and mechanics: "How does deep strike work?"
- **A SQLite database of unit datasheets**, for specific data: "How many points do Boyz cost?"

Some questions need both: "What does Stealth do, and which Tyranids units have it?" The system
decides which source to use on each turn, keeps track of the conversation, and cites where each
answer came from.

**Constraints**

- The LLM is Google AI Studio (Gemini) only, so a reviewer only needs to supply their own key.
- It must run on a laptop. Embeddings run locally and the vector database is a local file.
- The database connection is read-only on every LLM-reachable path.

**Out of scope:** a graphical interface (the interface is a command-line chat) and ColBERT / late
interaction.

## 2. Architecture

```
OFFLINE (built once)

  Core Rules.pdf --docling--> parsed JSON --chunker--> 261 chunks --bge-small--> ChromaDB

  wahadb.sqlite + data dictionary --> schema text, join graph, value index
  Hand-written question-to-SQL pairs --> few-shot pool

ONLINE (one chat turn)

  question + earlier turns
          |
          v
  Contextualize (LLM, follow-ups only): rewrite into a standalone question
          |
          v
  Router (LLM, JSON): pdf | sql | both.  On failure: pdf
          |
    +-----+---------------- both: split into two sub-questions ---+
    |                                                             |
    v                                                             v
  PDF retriever                                         Text-to-SQL agent
  embed query, top-5 chunks                             match values + pick 5 examples
  with page and section                                 LLM writes SQL, run read-only,
    |                                                   retry on error or nothing found (3 max)
    |                                                             |
    +----------------------------+--------------------------------+
                                 v
              Answer generation (LLM): cites pages and SQL
                                 |
                                 v
                 FinalAnswer, added to the conversation
```

### Main design decisions

| Decision | Why | Alternative considered |
|---|---|---|
| Two retrieval paths | Rules are prose and suit semantic search. Counts, lists and stats need exact computation, which similarity search cannot do. | One vector index over everything: cannot count or filter reliably. |
| LLM router, not always querying both | SQL generation is slow and costly, and irrelevant context can mislead the answer. | The keyword router this replaced sent "How do stratagems work?" to SQL because of a keyword. |
| Plain Python, no agent framework | The flow is short and fixed. Direct code is easier to read and test, and lets `FakeLlm` replace the LLM in tests. | LangChain / LangGraph add concepts this flow does not need. |
| One shared contract | `interfaces.py` lets the two paths and the router develop independently. | Modules importing each other's internals. |
| Fail softly per turn, loudly on setup errors | One API error should not end a chat, but a missing index should say what to do. | Crash on every error, or hide every error. |

| Database | `rag/data/raw/wahadb.sqlite` | 21 tables. Opened read-only. |
| Data dictionary | `rag/data/raw/SQL_AGENT_DATA_DICTIONARY.md` | Table and column descriptions, and join relations. |
| SQL examples | `rag/data/sql_examples.json` | 22 few-shot pairs for prompts and 14 held-out pairs for evaluation. |
| LLM cache | `rag/data/cache/llm/` | Responses keyed by a hash of model, temperature, prompt and schema. Git-ignored. |
| Evaluation results | `rag/data/eval_results/` | Reports, per-question records and analysis. |

### Database quirks that shaped the design

These were found by querying the data, and the dictionary does not always mention them:

- Every column is TEXT, so numeric comparison needs `CAST`. Movement is stored like `12"`.
- `datasheets.role` is always empty, even though the dictionary's example queries use it.
- Punctuation is mis-encoded: `’` is stored as `â\x80\x99`. Names containing it are matched with
  `LIKE`, and text is repaired before it reaches the answer.
- `invSv` is stored as `4` to mean 4+, or `-` for none.
- Rows in `datasheets_models_cost` with an empty cost are tier headers, not junk: many units cost
  more from the fourth copy onward.
- Core abilities have an empty name on the datasheet row and must be joined to `abilities`, while
  abilities unique to one unit are named directly on that row.
- Stratagems repeat across detachments, so counts need a decision about what counts as distinct.
- One datasheet is a placeholder (`virtual = 'true'`) and is excluded from counts.

## 5. PDF path

| Step | Choice | Why |
|---|---|---|
| Parsing | docling, reading its JSON | Docling's Markdown lost section headers on multi-column pages; the JSON keeps each element's label, page and position. |
| Cleaning | Remove page headers and footers, decorative numerals and OCR noise; repair headers with body text attached | These pollute both retrieval and section titles. |
| Chunking | A new chunk at every section header; split further past 1200 characters; tables kept in reading position | Each chunk stays on one topic and keeps page and section metadata. Result: 261 chunks. |
| Embedding | `BAAI/bge-small-en-v1.5` | Open source, small, runs locally with no API quota, and ranks well among small models on MTEB. Limit 512 tokens; the longest chunk with its title is 390. |
| Text embedded | `"{section}\n{text}"` | See below. |
| Query | Model card's query prefix | Recommended by the model card. It did not change rankings on its own in our check. |
| Store | ChromaDB, cosine | Simple local persistence. |
| Retrieval | Top 5, no reranking or keyword search | Baseline already hits every expected section; see below. |

### Effect of adding section titles

Before this change, both test questions below failed. Top-3 results, cosine score:

| Question | Without titles | With titles |
|---|---|---|
| How does deep strike work? | p49 EXAMPLE BATTLEFIELDS, p32 FIGHT PHASE, p32 FIGHTS FIRST | **p39 DEEP STRIKE (0.696)**, p33 FIGHT, p32 FIGHT PHASE |
| When do I determine the attacker and defender? | p57/p59 DECLARE BATTLE FORMATIONS, p33 MAKE MELEE ATTACKS | **p57/p59 DETERMINE ATTACKER AND DEFENDER (0.779)**, p60 DETERMINE VICTOR |

Section titles carry the topic that body sentences often leave out.

### Retrieval baseline

`make eval`, 20 labelled questions, k = 5: section hit 100%, page hit 100%, MRR 0.938. Two
questions rank below first: `saving-throw` (rank 4, "roll" attracts other sections) and
`battle-shock` (rank 2). BM25 fusion is the likely fix, but with so few failures it was not added.
Two of these questions were used while tuning, so the score is somewhat optimistic.

## 6. SQL path

### Pipeline

```
question
  |-- match_values()     stored names mentioned in the question
  |-- select_examples()  5 most similar question-to-SQL pairs
  |-- render_schema()    all tables, columns, statistics, joins
  v
prompt (rules + schema + value hints + examples + question)
  v
LLM returns {reasoning, sql}
  v
run_sql(): read-only, safety limits
  |-- error, no rows, or a lone 0 --> feed back and retry (3 attempts)
  v
SqlRagResult(sql, rows, columns, error, total_rows)
```

### Choices

| Component | Choice | Why |
|---|---|---|
| Schema context | Dictionary descriptions merged with live statistics; all 21 tables | Statistics correct the dictionary. See the pruning experiment. |
| Join graph | Parsed from the dictionary, since the database has no foreign keys; `factions` weighted as a hub | Stops the LLM guessing join columns. Without the weight, most tables appear connected through `factions`. |
| Value index | 10,438 names across 10 columns: exact, then fuzzy (`fuzz.ratio` ≥ 88), then partial words | Maps "Boyz" or "lascanon" to stored literals. `WRatio` was tried first and was too noisy. |
| Few-shot selection | Fuzzy text match plus embeddings, merged by reciprocal rank fusion; 5 examples | See the experiments. |
| Domain rules | Short rules in the prompt, such as `CAST`, ties, and abilities versus keywords | Encodes the database quirks in section 3. |
| Safety | `mode=ro`, a SQLite authorizer, SELECT/WITH only, 10 s timeout, value size cap | LLM output is untrusted. The authorizer is enforced by SQLite itself, so text tricks cannot get past it. |
| Row cap | 50 rows returned, true total reported | Protects the prompt, without letting the LLM mistake 50 for the total. |
| Retry | On an error, no rows, or a lone 0 | A count over the wrong table returns one row (0), so checking only for empty rows would miss it. Repeating the same query is accepted as a final answer. |
| Output | Structured JSON | No parsing of free-form text. |

### Experiments

These compared alternatives on 36 questions: the 14 held-out questions, the SQL parts of the 8
`both` questions, and 14 new ones. They ran SQL only, on `gemini-3.1-flash-lite`, before the
current rules and examples were added. "Correct" means the data was right after reading each
mismatch, because some automatic mismatches were only extra or missing columns.

**Schema pruning.** The alternative searched table descriptions with embeddings and BM25, added
tables from value matches, kept 5, then added whatever joins required.

| Configuration | Exact | Relaxed | Correct | Prompt tokens per question |
|---|---|---|---|---|
| Full schema, text-match examples | 30 | 33 | 35 | 7065 |
| Full schema, hybrid examples | 28 | 32 | 35 | 6940 |
| Pruned schema, text-match examples | 29 | 32 | 34 | 3430 |
| Pruned schema, hybrid examples | 29 | 31 | 34 | 3295 |
| Pruned plus example tables, hybrid examples | 29 | 32 | 35 | 3712 |

Pruning halves the prompt with no accuracy gain, and adds the risk of leaving out a needed table.
With only 21 tables the prompt fits comfortably, so **the full schema stays**. Table search alone
was weak: with embeddings or BM25 alone, needed tables were all kept for only 39% to 72% of
questions, rising to 97% once value matches were added. Pruning would become worthwhile with a
much larger schema.

**Few-shot selection on informal wording.** The first comparison favoured text matching, because
the test questions and examples shared wording. So 34 questions were reworded informally, with
the same answers ("priciest tyranid enhancement?", "what can ghaz lead"). One rewording changed
the question's meaning and was excluded, leaving 33.

| Method | All needed tables in examples: standard wording | Informal wording | SQL correct, informal (of 33) |
|---|---|---|---|
| Text match | 71% | 59% | 29 |
| Embeddings | 76% | 68% | 30 |
| Hybrid | 76% | 71% | 30 |
| No examples | | | 28 |

The same 33 questions with standard wording gave 32 correct for text match, so informal wording
does cost accuracy. Hybrid selection held up better and needs no new dependency or API call,
because the PDF path already loads the embedding model. The differences in correct answers are
small, and examples matter less than the rules: no method fixed the errors caused by confusing
abilities with keywords. Those errors led to the current rules and examples.

**Number of examples.** After adding two examples, on the same informal questions:

| Method | 3 examples | 5 examples |
|---|---|---|
| Text match | 59% | 76% |
| Embeddings | 76% | 91% |
| Hybrid | 71% | 88% |

Two more examples add about 3% to the prompt, so the system uses **5**. Embeddings scored
slightly higher than hybrid, by one question; hybrid was kept because it also keeps exact wording
matches.

**Value matching.** Every name or keyword literal in the gold SQL was found by the value index (59
of 59), so this step was left as it is. This covers only names and keywords.

These experiments were run with temporary scripts that are not in the repository.

## 7. Router

| Choice | Why |
|---|---|
| LLM classification into `pdf`, `sql` or `both` | Decides on meaning, not keywords. |
| JSON output limited to those three values | Invalid values are caught instead of being passed along. |
| Examples in `router_examples.py` | Teach the boundary between rules and data, and how to split `both`. |
| Falls back to `pdf` on failure | Rules questions are common, and the rulebook is a safer default than an unreliable query. |
| `both` splits the question | Each retriever gets only its own part. The split must keep every condition from the original question: losing "in the Fight phase" once produced a wrong answer. |

## 8. Answer generation and conversation

- **Answer prompts** differ by source. PDF answers cite each claim like `(p. 39)` and must say when
  the excerpts do not cover the question. SQL answers lead with the result and end with the query
  under `Source:`. Both requirements exist so a user can check the answer.
- **Partial lists:** when rows are cut off, the prompt receives the true total and is told to say
  the list is partial.
- **Follow-ups:** with history, `_contextualize` rewrites "what about Orks?" into a standalone
  question before routing, because retrieval and SQL have no memory. Only recent turns are used.
- **Failure:** if generation fails, the user sees the retrieved material with a note, not an error.
- **Chat commands:** `/help`, `/reset`, `/history`, `/last`, `/sources`, `/zh`, `/fr`, `/en`,
  `/quit`. `/sources` shows the chunks or SQL behind the last answer.

## 9. LLM layer

`GeminiLlm` in `llm/gemini.py` is passed to every component that needs a model.

| Feature | Why |
|---|---|
| Disk cache | Saves quota, makes reruns cheap, and lets interrupted evaluations resume. |
| Retries on 429, 5xx and network errors | Transient failures should not end a turn. |
| Waits as long as the server asks; fails fast past 120 s | A per-minute limit is worth waiting for; a used-up daily quota is not. |
| `min_interval_s` / `GEMINI_MIN_INTERVAL_S` | Spaces out calls to stay under a rate limit. |
| Usage tracking | Calls, tokens and time, printed after evaluations. |
| `FakeLlm` | Tests run with scripted replies, with no network or key. |

**Models.** The chatbot defaults to `gemini-3.5-flash`, currently served by `gemini-3.6-flash`.
Override it with `GEMINI_MODEL`. On the free tier this model allows about 5 requests per minute
and 20 per day, and one question takes 2 to 3 calls, so a free key should set
`GEMINI_MIN_INTERVAL_S=12`, and will run out after a few questions. RAGAS judges with
`gemini-3.1-flash-lite` (15 per minute and 500 per day on the free tier), because scoring makes
several times more calls than answering.

## 10. Evaluation

Three layers, so a failure can be traced to its cause:

| Command | Scope | Measures | LLM calls |
|---|---|---|---|
| `make eval` | PDF retrieval | Section and page hit@5, MRR | None |
| `make eval-sql` | SQL agent | Execution accuracy against gold SQL | About 1 per question |
| `make eval-e2e` | Whole system | Routing, retrieval, SQL, RAGAS | About 530 on an empty cache |

### End-to-end question set

`rag/src_rag/evaluation/questions_e2e.jsonl` has 40 questions, written by hand with AI assistance:

| Group | Count | Source | Answer key |
|---|---|---|---|
| PDF | 14 | Rules questions, minus any used as router examples | Reference answer, expected pages and sections |
| SQL | 14 | Held-out questions in `sql_examples.json` | Reference answer, gold SQL |
| Both | 8 | Written for this set | Reference answer, sections, gold SQL |
| Course questions | 4 | The four questions listed in the course | Reference answer; expected sections for three |

A test checks that none of them appears in a router or SQL few-shot prompt, which would inflate
the scores. "What is the toughness of a space marine?" has no gold SQL result, because it spans many
datasheets.

### Metrics

| Metric | Question it answers | Scored by |
|---|---|---|
| Router accuracy | Was the right source chosen? | Label |
| PDF section / page hit@5 | Was the right passage retrieved? | Label |
| SQL exact match | Is the result the same as the gold result? | Program |
| SQL relaxed match | Is the gold result contained, with extra columns allowed? | Program |
| Faithfulness | Is the answer supported by the retrieved context? | RAGAS |
| Answer relevancy | Does the answer address the question? | RAGAS |
| Context precision | Is the retrieved context useful? | RAGAS |
| Context recall | Does the context cover the reference answer? | RAGAS |
| Answer correctness | Does the answer agree with the reference? | RAGAS |

RAGAS alone is not enough for SQL: if a query is wrong, an answer can still be faithful to its wrong
rows and score well. So SQL results are also compared with gold results.

### Scoring details

- **Quota failures are not scored.** If an LLM call fails on a question, it is marked incomplete.
  Otherwise the router's fallback to PDF would count quota errors as correct routing.
- **The SQL citation is removed before RAGAS scores an answer.** Otherwise RAGAS treats query
  details as false claims: a sentence identical to the reference scored 0.587 with the citation,
  and 1.000 without it.
- **Adapters:** `ragas_adapters.py` connects RAGAS to our Gemini wrapper, so judging is cached and
  rate-limited, and to the local embedding model.

## 11. Results

Latest end-to-end run: 40 questions, chatbot on `gemini-3.5-flash`, judge on
`gemini-3.1-flash-lite`, no failed questions. Per-question scores are in
[`e2e_report.md`](rag/data/eval_results/e2e_report.md), and the analysis in
[`e2e_analysis.md`](rag/data/eval_results/e2e_analysis.md).

| Metric | Overall | PDF (17) | SQL (15) | Both (8) |
|---|---|---|---|---|
| Router accuracy | 40/40 | 17/17 | 15/15 | 8/8 |
| PDF section hit@5 | 25/25 | 17/17 | | 8/8 |
| SQL exact match | 14/22 | | 7/14 | 7/8 |
| SQL relaxed match | 22/22 | | 14/14 | 8/8 |
| Faithfulness | 0.963 | 0.977 | 0.939 | 0.980 |
| Answer relevancy | 0.917 | 0.874 | 0.949 | 0.951 |
| Answer correctness | 0.797 | 0.721 | 0.875 | 0.812 |
| Context recall | 0.985 | 0.966 | 1.000 | 1.000 |
| Context precision | 0.662 | 0.676 | 1.000 | 0.000 |

The PDF group includes three of the course questions, and the SQL group includes the fourth, which
has no gold result. That is why SQL match counts 14 questions in that column, not 15.

**How to read these numbers**

- **Routing and retrieval work well here.** Every question reached the expected source, and every
  expected section was in the top 5.
- **Exact SQL match understates the result.** All eight mismatches returned the right rows with
  extra columns, for example also returning the unit's name.
- **Context precision of 0.000 on `both` is a measurement artefact.** RAGAS judges each chunk alone,
  and one chunk cannot support a two-part answer. Section hit on those questions is 8/8.
- **Answer correctness also penalises extra detail.** `s-e09` is correct, but explains the ability
  beyond the reference and scores 0.404.
- **These scores are probably optimistic**, for the reasons in [section 12](#12-known-limitations).
  In particular, the latest rules were written after seeing errors on these same questions.

**Where the system is really weak**

| Question | Problem |
|---|---|
| How is the wound roll calculated? (`p-wound-roll`) | The table's values are lost in parsing. The answer correctly says they are missing, but cannot give them all. |
| What is the toughness of a space marine? (`t-toughness-space-marine`) | A broad question: only 50 of 293 rows reach the answer, which then generalises past what it saw (faithfulness 0.364). |
| What are the different ways to score points? (`t-score-points`) | The answer spans several sections and top-5 retrieval finds only part of it (context recall 0.667). The answer says it is incomplete. |

An earlier run, before the current SQL rules and on a different model, is kept in
[`before_sql_improvements/`](rag/data/eval_results/before_sql_improvements/). The model, the
question count and three gold answers all changed between the runs, so the two sets of scores are
not directly comparable.

## 12. Known limitations

- **Evaluation set:** small, and the SQL questions resemble the few-shot patterns, so scores are
  likely optimistic. Reference answers and gold SQL were written with AI assistance and reviewed by
  hand.
- **Judge:** the RAGAS judge is a cheaper model than the chatbot, and its single-question scores
  are noisy. A stronger judge would be better.
- **Tuning on seen questions:** the rules and examples were added after seeing errors on these
  questions, so improvements on them overstate the real gain. Testing needs fresh questions.
- **Parsing:** values printed as images are lost. The wound roll table's dice values are missing and
  the table is filed under the wrong section and page. Answers about it are incomplete, and an
  earlier run on a cheaper model filled in the values from its own knowledge.
- **Broad data questions:** only 50 rows reach the answer, so a question spanning hundreds of rows
  can be generalised beyond what the model saw.
- **PDF retrieval:** embeddings only, so exact terms can be outranked ("save roll" attracts other
  "roll" sections).
- **SQL:** retries catch errors and empty results, not a query that returns plausible but wrong
  rows. Ambiguous names ("intercessors") may be read more broadly than intended.
- **Monitoring:** usage is reported per run, not per question.
- **Quality tooling:** no linter or pre-commit hook is configured.
- **Free-tier quota:** the default chatbot model's free tier allows only a few questions per day.

## 13. Possible next steps

In rough order of expected value:

1. Add questions from real use to the evaluation set.
2. Add the wound table's values to its chunk and correct its page.
3. Add BM25 fusion to PDF retrieval, for exact terms.
4. Use a stronger RAGAS judge.
5. Record latency and tokens per question.
6. Add ruff and pre-commit.

## 14. How to extend the system

| To change | Where | Then |
|---|---|---|
| The embedding model | `MODEL_NAME` in `retriever/pdf.py` | Run `make index` and `make eval` |
| The chunking | `chunker/chunk.py` | Run `make index` and `make eval` |
| SQL rules | `RULES` in `retriever/sql_rag.py` | Run `make eval-sql` |
| Few-shot examples | `rag/data/sql_examples.json`, then `uv run python -m rag.src_rag.retriever.sql_examples --update-expected` | Check `git diff` and update counts in `test_sql_examples.py` |
| Routing behaviour | `chatbot/router.py`, `router_examples.py` | Run `make eval-e2e` |
| A shared type | `interfaces.py` first, then both sides | Run `make test` |
| The LLM provider | Implement the `Llm` protocol | Pass it to `answer()` |

Project rules for contributors, such as tests mirroring the source layout and secrets in `.env`,
are in [`AGENTS.md`](AGENTS.md).
